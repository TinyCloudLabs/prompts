## Observed registry decoding defect

Installed CLI 0.10.0's AccountService reads a canonical registry value as an object even when KV returns JSON text. A direct local KV read contained one manifest, while account info for the same key returned none. A second source-level regression probe reproduces that loss and verifies explicit canonical normalization recovers the record. The precise HTTP content-type explanation is source-supported; the returned string and discarded manifests were directly observed.

The guide and enrollment recipe now use existing `kv get applications/APP_ID --space FULL_ACCOUNT_SPACE --json` when metadata is incomplete, parse only the envelope's `data` once if it is a string, and validate the resulting record. This uses the already granted registry get scope. No SDK patch or new loader was introduced. Do not conclude that a tracker is unenrolled solely from empty account-API manifest arrays.

## Live acceptance status

An actual fresh Codex CLI process was started outside the development/playground instruction ancestry. Its only task inputs were this guide, the original sample weight question, the documented hosted server, and the instruction to use an isolated project-local installation/home. It installed CLI/core skill 0.10.0 using the pinned installer, created its own reader context, and launched OpenKey. No app locator, CSV, prior answer, operator context or OpenCode adapter was supplied.

The browser path did not save owner identity; a supported context read returned `ADDRESS_UNKNOWN`. Source inspection and a synthetic callback establish that loopback exists, but do not determine whether browser delivery, process lifetime, timeout or proof validation caused this failure. The human then completed the CLI's direct Terminal `--paste` flow. Authorization responses were not transferred by the implementation into tool arguments or generated scripts.

A new Codex process reused the saved owner context and successfully ran hosted `apps list --live`, returning four applications with empty decoded manifests. It accurately reported that it had not read the records, but its inference of missing enrollment was premature because the decoder defect had not yet been incorporated into the guide. That failed acceptance observation led to the explicit canonical KV procedure above. The one-hour test grant later expired; the human renewed the same registry scope for the same owner using the CLI's seven-day default duration. Expiry was detected through supported context and an explicit expired-session error, without reading credential files.

A third fresh Codex process followed the corrected guide and reused the renewed saved context. Live canonical KV reads recovered three valid application manifests, none describing weight tracking or a knowledge root. A fourth canonical record used a singular `manifest` field instead of the required `manifests` array; the agent reported that format error without rewriting it. It stopped at the enrollment/guidance gap and did not query app data or fabricate averages. This verifies hosted registry authentication, fresh-process reuse, canonical normalization, and the missing-guidance stop behavior.

Separate operator-only preflight confirmed that the existing tracker catalog has the expected format and two targets at unchanged locations, while the proposed registry key and knowledge root explicitly return `NOT_FOUND`. Those operator locators were not given to any fresh retrieval agent. Concrete local enrollment files were prepared, but no owner enrollment write or permission expansion was performed. Owner approval is the next gate.

The user subsequently authorized completing local enrollment and the short-prompt experience. A separate owner enrollment profile obtained registry get/list plus put on the single tracker key. The knowledge root and registration were added and verified through live canonical reads. Existing records, intentions, catalog and domain guidance matched private before/after content hashes. No schema or observation changes were made. The setup recipe now puts `--` before its YAML document argument: without it, CLI 0.10.0 rejects leading `---` as an option before dispatch.

The local short entry carries host context and optional durable reader selections, with no app location or answer. A new Codex process in a fresh directory received `Compare my avg weight in Aug vs Mar. Check TinyCloud: <local-entry-path>` (the personal path is redacted here). It inferred 2026, used saved registry access, discovered the enrolled tracker and independently requested only private KV get, fitness SQL read and capabilities read. The human completed that consent through the direct Terminal.

Another independent Codex process received the identical one-line prompt in an empty directory. It reused both grants without fresh consent, discovered the tracker through live registry and canonical reads, read the knowledge root/catalog/guidance, inspected `sqlite_master`, and queried actual records. Its means, units, counts, occurrence-date coverage and August-minus-March difference matched an independent live query. It stated the year assumption and that irregular recorded readings are not daily averages. The 19-command question run had no authentication changes, registration, index rebuild, data mutations or sharing. Actual health values remain private rather than embedded in this guide or shared evidence.

A separate hosted scope test verified that a random synthetic table did not exist, then attempted an insert into only that nonexistent table. It received explicit `AUTH_UNAUTHORIZED`; no real user table or record was targeted and no schema changed. Full short-prompt retrieval and fresh-process reuse are verified for this selected owner/host and saved grants. Consent is still a human action and must be renewed when access expires. The guide's CLI decoding workaround remains necessary for the tested release. Existing exports and running client remain unchanged. The reader's CLI-managed state was moved intact from temporary to durable storage and verified through `context`; credential files were not inspected.

Missing enrollment is a precise owner setup gap; adding reader instructions cannot make an unregistered app discoverable. Hosted account access and owner context must also be verified independently of existing app-data reads. ## October 2, 2026: fixture decoupling

The [query probe](validation/retrieval-query-probe.py) now owns its disposable SQLite query instead of extracting SQL from guide prose. Its fixture-specific schema and domain are not generic application requirements. The implementation parent ran it successfully after this change: half-open occurrence-date boundaries, capture-date independence, multiple readings per day, exclusion of unrelated metrics, separate units, mean difference, missing-month nulls and empty-dataset nulls remain checked. The query uses bound parameters and never contacts TinyCloud or user data.

The September 29 statement that the probe executed the guide's SQL remains historical evidence. The new probe does not prove that an agent generated a correct query or followed the new public entry. Current runner modes, private evidence, publication/consent gates and unexercised public journeys are documented in the [October 2 runner update](app-creation-validation.md#october-2-2026-public-entry-runner-boundary).
